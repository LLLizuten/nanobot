# 投资助手补缺设计文档

## 背景与目的

`2026-04-26` 的一期设计与五份实现计划已经基本落地，但浮浮酱在对照 `docs/superpowers` 与当前实现时发现，仍有几项属于“原设计已承诺、当前实现未完全覆盖”的缺口。

本文件不是重写一期方案，也不是开启二期扩张，而是为后续补缺工作定义清晰边界、目标和验收标准，避免实现过程中范围漂移。

本轮补缺只处理以下三类问题：

1. 技术信号引擎尚未真实产出 `减仓 / 卖出` 信号
2. 调度层尚未接入真实的 A 股交易日历，法定休市日仍按普通工作日处理
3. 聊天命令尚未提供“查询某个标的或当前持仓最新状态”的动态能力

## 当前未对齐项

### 1. 卖出侧信号未真正打通

当前 `decisions.py` 已经支持把 `reduce / exit` 翻译成 `减仓 / 卖出`，但 `signals.py` 实际只会稳定产出 `entry` 或 `watch`。这意味着：

- 系统具备卖出侧动作的接口定义
- 真实扫描链路却无法稳定触发这些动作
- 设计文档中关于技术位止损、移动止盈、趋势转弱处理的承诺还没有真正落实

这属于功能链路中段缺失，而不是消息文案或存储层缺失。

### 2. 法定休市日未纳入调度约束

当前后台服务默认通过“周一到周五 + 交易时段”判断是否运行巡检，尚未接入中国市场真实交易日历。这意味着：

- 周末过滤是正确的
- 午休与收盘时段过滤是正确的
- 但法定休市日、调休交易日无法正确识别

一期原始设计要求常规播报在法定休市日不发送，因此这里属于设计与实现之间的真实偏差。

### 3. 缺少动态状态查询能力

当前 `/invest` 命令支持维护自选池、持仓、模式和扫描周期，也支持 `/invest show` 查看静态已保存状态，但尚未支持：

- 查询单个标的的最新技术状态
- 查询当前持仓标的的最新动作建议

这使得投资助手当前更像“被动定时播报 + 静态配置维护”，而不是“可随时按需查询最新状态”的助手。

## 补齐目标

### 目标 1：让卖出侧信号成为真实输出，而不是预留接口

补齐后，信号引擎必须能基于已收盘完整 K 线，真实产出以下状态：

- `entry`
- `watch`
- `reduce`
- `exit`
- `hold`

其中：

- `entry` 用于无持仓或可继续加仓的趋势延续场景
- `reduce` 用于动能转弱但趋势尚未完全破坏的场景
- `exit` 用于突破失败或趋势结构失效的场景
- `hold` 用于已有持仓且趋势依旧健康、无需新增动作的场景

补缺完成后，后台扫描与按需查询都必须能走到同一套卖出侧判断逻辑，不能出现“命令能看见、定时扫描看不见”或反之的分叉实现。

### 目标 2：让调度层按真实中国交易日运作

补齐后，投资助手的后台播报必须同时满足：

- 仅在 `09:30-11:30`、`13:00-15:00` 的交易时段运行
- 周末不发送常规播报
- 法定休市日不发送常规播报
- 调休形成的实际交易日可以正常播报

如果交易日历源不可用，系统应优先选择“保守不播报”的失败策略，而不是退回到不可靠的工作日近似判断后继续发信号。

### 目标 3：让聊天入口具备动态查询能力

补齐后，聊天入口应同时支持以下两类查询：

- 查询单个标的的最新技术与动作状态
- 查询当前持仓集合的最新状态摘要

为避免与现有 `/invest show` 的静态配置展示语义冲突，本轮补缺建议新增独立子命令：

- `/invest status <symbol>`
- `/invest status positions`

其中：

- `/invest show` 继续负责展示静态已保存状态
- `/invest status ...` 负责拉取最新完整周期行情并即时计算结果

## 方案约束

### 保持现有分层，不推翻一期结构

本轮补缺必须复用现有职责边界：

- `data.py`：行情获取与标准化
- `signals.py`：技术状态判断
- `decisions.py`：持仓感知动作翻译
- `reporting.py`：消息排版
- `service.py`：后台调度与发布
- `command/investment.py`：聊天命令入口

不应为了补缺而把命令、调度、信号判断重新揉成单一大模块。

### 共享一套分析流水线

动态查询与后台扫描都需要执行“拉取行情 -> 产出技术信号 -> 翻译动作建议”这一流水线。为避免重复逻辑，本轮补缺应提炼共享分析入口，使以下两个场景复用同一逻辑：

- 定时扫描
- `/invest status ...` 即时查询

允许新增小型应用层辅助模块，但不应复制一套平行判断逻辑。

### 保持一期范围克制

本轮补缺不包含以下内容：

- 自动下单
- 盘中未收盘 K 线抢跑
- 全市场扫描
- 图形化看板
- 复杂仓位模型
- 多策略并行框架

补缺目标是把一期承诺补完整，而不是把产品推向二期。

## 详细设计

### 卖出侧信号补齐

信号引擎继续以“趋势突破策略”作为唯一策略家族，但在已有 `entry/watch` 之外补齐持仓后的趋势维护状态。

建议把卖出侧判断收敛为两层：

1. `reduce`
   适用于趋势明显转弱，但尚未确认彻底失效的场景。
   建议最小判定口径：
   - 最新收盘价跌破短期均线，但仍未明显跌破中期均线
   - 或突破后出现明显动能衰减 / 放量滞涨，尚不足以定义为结构性失效

2. `exit`
   适用于趋势结构已经被破坏的场景。
   建议最小判定口径：
   - 突破失败，价格回到突破位下方，并在连续两根已收盘周期 K 线内未能收回
   - 或关键短中期均线关系转坏，且最新收盘价同步失守中期趋势参考

对于已有持仓但趋势继续健康的场景，信号层应直接返回 `hold`，而不是继续返回 `watch`。这样决策层与消息层可以更清楚地区分“无机会等待”和“有持仓继续持有”。

### 交易日历补齐

当前 `service.py` 已经预留 `is_open_day` 可注入点，因此本轮补缺不应改写时段调度框架，而应补上真实交易日判断实现。

建议新增轻量交易日历适配层，职责包括：

- 判断某一自然日是否为中国市场开市日
- 提供按年或按日期范围缓存能力，减少重复请求
- 在依赖不可用或数据获取失败时，向上层返回“无法确认是否开市”

后台服务的处理策略建议如下：

- 能确认开市：按正常流程扫描
- 能确认休市：直接跳过
- 无法确认：记录告警并跳过常规播报

这样可以保证“宁可少发，不可误发”。

### 动态查询补齐

聊天命令层需要新增动态查询入口，但不应自行实现信号规则。命令层职责仍然只包括：

- 参数解析
- 输入校验
- 调用共享分析入口
- 格式化回复

建议新增两条命令：

1. `/invest status <symbol>`
   返回内容至少包含：
   - 标的代码与资产类型
   - 最新已收盘周期时间
   - 当前技术状态
   - 当前建议动作
   - 触发原因
   - 失效条件
   - 风险提示
   - 若当前有持仓，则展示当前仓位档位与 `T+1` 可执行性

2. `/invest status positions`
   针对当前所有持仓标的批量给出最新状态摘要，并突出正式信号变化。

若用户查询的标的不在自选池中，系统可以允许即时查询，但必须要求用户显式提供资产类型，或给出清晰错误提示；本轮补缺的最小版本也可以限定“只允许查询自选池和持仓中已有标的”，以保持实现简单。

本轮推荐采用后者，即：

- `/invest status <symbol>` 仅支持查询已存在于自选池或持仓中的标的
- 若符号不存在，直接返回可理解的错误提示

这样能避免在命令层额外引入资产类型推断。

## 验收标准

补缺完成后，至少应满足以下验收条件：

### 信号与决策

- 给定构造好的完整 K 线序列，`signals.py` 能稳定产出 `entry / hold / reduce / exit / watch`
- `decisions.py` 对 `reduce / exit` 的翻译在真实扫描链路中可被触发
- 同日买入后出现 `reduce / exit` 时，仍遵守 `T+1` 标记为“当前不可执行”

### 调度与交易日历

- 普通交易日的交易时段内可正常扫描与播报
- 周末不播报
- 法定休市日不播报
- 调休交易日可播报
- 交易日历不可用时不会错误发送常规播报

### 聊天查询

- `/invest show` 仍保留原有静态状态展示行为
- `/invest status <symbol>` 能返回单标的最新状态
- `/invest status positions` 能返回当前持仓集合的最新状态
- 聊天查询与后台扫描对同一标的的技术状态和动作建议保持一致

### 代码结构

- 不出现复制粘贴式的第二套信号判断逻辑
- 命令层不直接内嵌行情抓取细节与策略规则
- 新增测试覆盖命令、信号、服务和交易日历边界行为

## 实施优先级

建议按以下顺序补齐：

1. 动态查询能力
   价值最高、反馈最快，也能倒逼抽出共享分析流水线
2. 卖出侧信号
   直接补足一期最重要的风险控制承诺
3. 真实交易日历
   解决调度准确性问题，避免节假日误报

这个顺序的原因是：先补查询能力最容易暴露共享逻辑边界问题；在共享入口稳定后，再补卖出侧状态会更自然；交易日历最后补，不会阻塞前两项的领域逻辑实现。

  - 批量持仓查询支持部分成功结果，并列出运行时失败的标的；行情依赖缺失按不可恢复错误返回友好提示。
